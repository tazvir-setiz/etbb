# وضعیت پروژه و نقشهٔ راه ادامهٔ کار

این سند برای تحویل پروژه به یک چت‌بات یا توسعه‌دهندهٔ دیگر نوشته شده است. پیش از شروع، `AGENTS.md` و این فایل را بخوانید. مخزن: `D:\Habib\etbb`؛ شاخهٔ کاری فعلی: `master`.

## خلاصهٔ یک‌دقیقه‌ای

پروژه یک ربات فارسی ارزیابی افراد است که با یک کد روی Telegram یا Bale اجرا می‌شود. مدیر از پنل جداگانه، افراد و نظرسنجی‌های زمان‌دار را مدیریت می‌کند؛ ارزیاب در منوی خودش برای هر فرد در هر نظرسنجی امتیاز ثبت می‌کند.

**مرحلهٔ جاری:** مراحل ۱ تا ۶ آماده‌اند؛ قدم بعدی مهاجرت نسخه‌دار پایگاه داده (مرحلهٔ ۷) است.

**آخرین کامیت پیاده‌سازی پیش از تهیهٔ این سند:** `021a9c3 feat: add editable person profiles`. برای آخرین کامیت مخزن پس از این سند، `git log -1 --oneline` را اجرا کنید.

## هدف و تصمیم‌های معماری که باید حفظ شوند

- دامنه، ارزیابی **افراد** در نظرسنجی‌های مستقل و زمان‌دار است؛ مدل عمومی `question/response` جایگزین مناسبی برای این دامنه نیست.
- هر رأی به یک فرد در یک نظرسنجی مربوط است. قید یکتایی فعلی `(survey_id, person_id, user_id)` اجازهٔ یک رأی برای هر فرد به هر رأی‌دهنده در همان نظرسنجی را می‌دهد.
- `SurveyPerson` مشخص می‌کند کدام افراد در یک نظرسنجی ارزیابی می‌شوند. `Vote` امتیاز و نظر را نگه می‌دارد.
- ناشناس‌بودن در گزارش و خروجی است: شناسهٔ رأی‌دهنده برای جلوگیری از رأی تکراری و نمایش «امتیازهای من» در پایگاه می‌ماند؛ خروجی نظرسنجی ناشناس هویت رأی‌دهنده را نشان نمی‌دهد.
- مدیر با `ADMIN_USER_IDS` در پلتفرم انتخاب‌شده تعیین می‌شود. پیام‌های مدیریتی و callbackها مجوز را دوباره بررسی می‌کنند. پنل مدیر از منوی ارزیاب جداست و مدیر با «حالت ارزیاب» جابه‌جا می‌شود.
- `BOT_PLATFORM=telegram|bale` پلتفرم اجرا را انتخاب می‌کند. توکن باید متعلق به همان پلتفرم باشد. منطق رأی‌گیری مشترک است.
- افراد دارای سابقهٔ رأی حذف فیزیکی نمی‌شوند؛ غیرفعال‌کردن آن‌ها مانع حضورشان در نظرسنجی‌های تازه می‌شود و سوابق قبلی را حفظ می‌کند.

## مراحل باقی‌مانده تا نسخهٔ کامل

هر مرحله را پس از پیاده‌سازی و بررسی معیارهای پذیرش تیک بزنید. اگر بخشی انجام شد، همان را در توضیح مرحله بنویسید و تا تکمیل معیارها `[ ]` را حفظ کنید.

### مرحلهٔ ۶ — چرخهٔ عمر نظرسنجی‌ها `[x]`

- ویرایش عنوان، توضیح، زمان و فهرست افراد از جزئیات نظرسنجی فراهم است؛ فقط نظرسنجی زمان‌بندی‌شده و بدون رأی و با شروع آینده قابل ویرایش است.
- افراد غیرفعال در فهرست ویرایش دیده می‌شوند تا بتوان آن‌ها را برداشت، اما افزودنشان ممنوع است.
- لغو نظرسنجی زمان‌بندی‌شده یا فعال تأیید جداگانه می‌خواهد؛ رأی‌ها و گزارش‌ها حفظ می‌شوند.
- وضعیت لغو در فهرست و جزئیات نمایش داده می‌شود و منطق رأی‌گیری رأی جدید برای آن نمی‌پذیرد.
- عملیات مدیریتی callbackها مجوز مدیر را دوباره بررسی می‌کنند و پیش‌نویس ویرایش پس از restart قابل بازیابی است.

**معیار اتمام:** ویرایش و لغو از رابط مدیر انجام می‌شود؛ قواعد وضعیت و سابقهٔ رأی حفظ می‌شوند و مسیرهای Telegram/Bale از همان منطق مشترک استفاده می‌کنند.

### مرحلهٔ ۷ — مهاجرت نسخه‌دار پایگاه داده `[ ]`

- ابزار migration نسخه‌دار مانند Alembic اضافه شود.
- وضعیت فعلی پایگاه‌های تازه و پایگاه‌های موجود، از جمله نسخه‌های SQLite و PostgreSQL، بدون حذف داده پوشش داده شود.
- ارتقای فعلی `users` از منطق دستی `initialize_database` به migrationهای قابل تکرار منتقل شود.
- baseline و روش امن برای پایگاه‌هایی که قبلاً با `create_all` ساخته شده‌اند مستند شود؛ از کاربر backup بخواهید و وضعیت واقعی DB را بررسی کنید، migration را کورکورانه اجرا نکنید.
- پس از آماده‌شدن migrationها، `create_all` برای تغییرات مدل در مسیر production به کار نرود.

**معیار اتمام:** یک پایگاه خالی از migrationها ساخته شود؛ یک پایگاه موجود آزمایشی با دادهٔ نمونه ارتقا یابد و شمار/روابط داده‌ها حفظ شود؛ مراحل backup و rollback مستند باشند.

### مرحلهٔ ۸ — افزودن گروهی افراد و بهبود گزارش `[ ]`

- ورود CSV/XLSX افراد با پیش‌نمایش، تشخیص شناسهٔ تکراری، گزارش ردیف‌های نامعتبر و تأیید نهایی اضافه شود.
- ورود گروهی نباید بخشی از فایل را بی‌خبر ثبت کند؛ نتیجهٔ موفق/ناموفق هر ردیف مشخص باشد.
- گزارش مدیر تعداد رأی‌دهندگان/پیشرفت را بدون افشای هویت در نظرسنجی ناشناس نشان دهد.

### مرحلهٔ ۹ — نقش مدیران و ثبت عملیات `[ ]`

- در صورت نیاز محصول، عضویت مدیران در پایگاه و نقش‌های روشن (مثلاً مالک/مدیر) اضافه شود؛ `ADMIN_USER_IDS` می‌تواند برای bootstrap مالک اولیه بماند.

- دسترسی همهٔ فرمان‌ها و callbackها با نقش لازم بررسی شود.

### مرحلهٔ ۱۰ — پوشش کیفیت و تجربهٔ کاربر `[ ]`

- تست‌های سرویس برای مرزهای زمان، مجوز، یکتایی رأی، لغو، تغییر نظرسنجی و سیاست ناشناس نوشته/به‌روز شوند.
- تست‌های جریان handler برای فرم‌های مدیر، callback قدیمی، بازیابی draft و ورودی نامعتبر اضافه شوند.
- ورودی تاریخ فارسی/لاتین و منطقهٔ زمانی تهران برای کاربر واضح باشد؛ خطاها قابل اصلاح باشند.
- تجربهٔ Telegram و Bale با هر کدام جداگانه smoke-check شود، شامل دکمه‌ها، متن، فایل Excel و callbackها.

### مرحلهٔ ۱۱ — آماده‌سازی انتشار و عملیات `[ ]`

- معیار پذیرش نهایی با مدیر پروژه/کاربر تأیید شود و یک نسخهٔ release مشخص کامیت/برچسب‌گذاری شود.

## وضعیت فنی فعلی و فایل‌های کلیدی

- Routerها: `app/bot/routers/admin.py` و `app/bot/routers/user.py`؛ `app/bot/handlers.py` فقط import سازگاری است.
- منوها و صفحه‌بندی: `app/bot/keyboards.py`.
- مدل‌ها: `app/models.py`؛ شروع DB: `app/database.py`؛ تنظیمات: `app/config.py`.
- قواعد رأی: `app/services/voting.py`؛ upsert کاربران: `app/services/users.py`؛ پیش‌نویس مدیر: `app/services/admin_drafts.py`.
- Excel: `app/exports/excel.py`.
- SQLite پیش‌فرض است؛ PostgreSQL از `DATABASE_URL` پشتیبانی می‌شود.
- FSM جاری in-memory است و فقط با `/start` از روی `admin_drafts` بازیابی می‌شود؛ رویدادهای جست‌وجو/صفحه‌بندی پیش‌نویس نیستند.
- migration عمومی هنوز وجود ندارد؛ `initialize_database` از `create_all` و یک ارتقای دستی قدیمی برای جدول کاربران استفاده می‌کند.
- مدیریت نقش‌های مدیر در پایگاه و import گروهی هنوز وجود ندارند. ویرایش/لغو نظرسنجی از پنل مدیر پشتیبانی می‌شود؛ ویرایش فقط پیش از شروع و پیش از نخستین رأی مجاز است.

## راه‌اندازی و بررسی

روی Windows و از ریشهٔ مخزن:

```powershell
.venv\Scripts\Activate.ps1
python -m app.main
```

`.env` باید محلی بماند. متغیرهای مهم: `BOT_TOKEN`، `BOT_PLATFORM`، `ADMIN_USER_IDS`، `DATABASE_URL` و `TIMEZONE`. برای اجرای بررسی‌های موجود:

```powershell
python -m pytest
python -m ruff check app tests
```

هنگام گزارش وضعیت، تفکیک کنید کدام بررسی واقعاً اجرا شده و کدام فقط پیشنهاد شده است.

هر بار که کد، پیکربندی یا مستندات پروژه تغییر می‌کند، همین سند را در همان مجموعه‌تغییر به‌روز کنید:

1. مرحلهٔ مرتبط را انتخاب کنید و فقط کارهای واقعاً تکمیل‌شده را `[x]` کنید.

3. اگر تصمیم معماری یا محدودیت تازه‌ای پیدا شد، آن را در همین سند ثبت کنید.
